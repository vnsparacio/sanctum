# V1.3 workflow reliability project

## Current-state diagnosis

Baseline inspected on 2026-09-20: accepted `v1.3-dev` commit `f09ee5d`.
The running owner installation uses Symphony `0.0.3` from commit `be10a1b`,
with the reviewed local permission-profile adapter changes and Codex CLI
`0.155.1`.

The observed restart problem is primarily an orchestration and environment
problem, not evidence that GPT-5.6 Sol is too weak:

- Sanctum overrides Symphony's 20-turn and one-hour-turn defaults with eight
  turns and a ten-minute turn timeout. The outer supervisor separately applies
  the same eight-turn concept in aggregate, a five-minute fixed stall limit,
  one hour total elapsed time, a small token ceiling, and a one-MiB dashboard
  output limit.
- TTE-9 receipts show stops at 513,245/500,000 tokens,
  1,572,908/1,500,000 tokens, and 1,050,039/1,048,576 output bytes. TTE-14
  receipts show two five-minute stall stops, a 5,073,708/5,000,000 token stop,
  repeated immediate stops against that persisted high-water mark, and two
  10/8 aggregate-turn stops.
- Every private incident says `linear_state_changed: false`. Symphony does not
  move active issues to Backlog. The owner used Backlog as a recovery switch
  because the supervisor only forgets an absent issue after 60 seconds; simply
  restarting with the issue active re-triggers the exhausted ledger.
- The worker workspace, branch, and workpad already survive ordinary Symphony
  continuation. The missing contract is a safe supervisor resume epoch that
  preserves those artifacts without requiring a Linear state bounce.
- TTE-9 and TTE-14 both reproduced the same deterministic managed-sandbox
  failure: `/bin/ps` cannot provide the process identity required by the Gate
  prelive test, while the owner-host full suite passes. Requiring the sandboxed
  worker itself to run that test makes completion impossible regardless of
  model quality.
- The Git control plane already records pending commit/push receipts before a
  mutation and reconciles uncertain results by stable operation ID. Reliability
  work should retain and test this boundary rather than expose credentials or
  arbitrary Git.

The repair therefore separates per-worker defense-in-depth limits from the
outer total budget, adds explicit resume semantics, delegates only approved
validation profiles to a host runner, classifies termination causes, keeps
Sol-medium as the standard worker, and adds a label-selected deep worker with
identical authority.

## Budget ownership and continuation

| Layer | Owns | Standard | Deep |
| --- | --- | ---: | ---: |
| Symphony worker | One Codex turn, per-worker silence, normal continuation | 20 turns, 60-minute turn timeout, 15-minute silence timeout | 30 turns, 60-minute turn timeout, 15-minute silence timeout |
| Sanctum supervisor | Total issue epoch across Symphony sessions | 6 hours, 40 turns, 8,000,000 tokens, 3 retries | 8 hours, 60 turns, 12,000,000 tokens, 3 retries |
| Sanctum supervisor | Process safety | 16 MiB captured service output, 30-second state-API grace | Same |

The supervisor no longer implements a second five-minute stall detector.
Symphony owns worker silence; Sanctum owns aggregate issue budgets and emits an
80-percent warning before exhaustion. Normal Symphony continuation preserves
the issue workspace, branch, workpad, and session history.

Symphony's state API reports turn and token counters cumulatively for the
running issue even though each continuation has a new session ID. The
supervisor therefore keeps one high-water mark per Symphony service invocation
and sums only across distinct service invocations in the same issue epoch. It
must not sum the cumulative value attached to every continuation session; that
would create triangular over-counting and a false budget stop. Legacy
session-keyed ledger entries are conservatively migrated to one cumulative
high-water bucket before a new service invocation is added.

A total-budget stop intentionally leaves Linear unchanged. After reviewing the
incident, the owner may start a new aggregate budget epoch without moving the
issue through Backlog:

```sh
.venv/bin/python -m sanctum_agents.cli symphony-resume \
  --incident "$SANCTUM_AGENT_PREFIX/incidents/<run-id>.json" \
  --issue TTE-123
```

The command accepts only a direct private incident that names the requested
issue and states that Linear was not changed. It archives that issue's old
ledger entry, writes an idempotent private resume receipt, and removes only the
exhausted ledger epoch. It does not mutate the workspace, branch, workpad, PR,
or Linear state. Record the incident and owner decision in the workpad before
running `symphony-run` again. Do not use resume to conceal a deterministic
blocker or failed validation.

## Host validation boundary

The worker remains sandboxed. A manifest-verified host MCP runner offers one
tool, `run_validation_profile`, with no arbitrary command parameter:

- `docs-config`: `git diff --check`, `make audit`, and `make verify-source`;
- `normal-code`: `make build`, `make test`, then the common checks;
- `architecture-security`: `make deps`, `make build`, `make test`, then the
  common checks.

The runner accepts only a leased issue workspace whose ID matches the Linear
issue. It uses fixed commands, per-command deadlines, a scrubbed environment,
no Linear or GitHub credentials, and private bounded output. Its idempotency
receipt binds the operation ID to the profile, commit, bounded Git delta, and
current contents of every changed or untracked file. The runner rechecks that
fingerprint after the commands, so a concurrent workspace change fails the
receipt. A stable operation ID cannot be reused after the workspace changes.

This resolves the TTE-9/TTE-14 `/bin/ps` mismatch: managed-sandbox failures are
classified as `SANDBOX`; the approved host profile supplies authoritative
validation evidence. The sandbox failure is not treated as a code failure,
and the agent receives no broader host shell authority.

## Failure classification and recovery

Every terminal reason maps to exactly one class:
`MODEL_REASONING`, `ENVIRONMENT`, `SANDBOX`, `VALIDATION`,
`GIT_CONTROL_PLANE`, `NETWORK_PROVIDER`, `TOKEN_BUDGET`, `TIME_BUDGET`,
`OWNER_ACTION_REQUIRED`, or `UNKNOWN`. Incidents and JSONL events contain only
safe operational metadata: issue, worker class, selected model/reasoning,
turn/retry counts, elapsed time, token counters when Symphony reports them,
limits, and receipt state. Prompts, source bodies, credentials, and private
file contents are excluded.

Recovery is deterministic:

- sandbox or validation mismatch: use the bounded host profile; do not deepen;
- ambiguous Git/GitHub result: reconcile the existing operation ID; do not
  replay with a new ID;
- token/time exhaustion: inspect the incident, preserve Linear state, and use
  the explicit owner resume only if more work is justified;
- network/provider/environment: preserve the checkpoint and retry only after
  the external condition is healthy;
- owner action: stop with the exact local checkpoint;
- repeated model-reasoning failure: request owner escalation to deep.

## Model routing

Routing is explicit and fail closed. Every authorized implementation issue
must have `symphony` and exactly one of:

- `agent-standard`: `gpt-5.6-sol`, medium reasoning, `WORKFLOW.md`;
- `agent-deep`: `gpt-6-astra`, high reasoning, `WORKFLOW.deep.md`.

Both workflows have the same filesystem, Git, validation, Linear, egress,
Human Review, and no-merge authority. Deep differs only in model, reasoning,
and budgets. Infrastructure or budget failures never trigger automatic deep
routing. The worker may request escalation after repeated
`MODEL_REASONING`; only the owner may replace the routing label and start the
deep supervisor. Global implementation concurrency remains one, and the two
worker classes share the same exclusive role lock and loopback state port.

The workspace-level labels were created on 2026-09-20 and were not applied to
any issue. Private metadata must still be recaptured before activation.
Existing issues are not silently migrated: the owner adds exactly one routing
label at the next authorization checkpoint.

## Git idempotency

Commit and push retain their existing pending-receipt/reconciliation contract.
Pull-request creation now uses the same stable operation-ID pattern: the broker
writes intent before the remote mutation, searches for an already-created PR
after an ambiguous response, and refuses a different intent under the same ID.
The worker must reconcile an unknown result and may not blindly create another
PR. This preserves one branch and one PR through continuation and Rework.

## TTE-49 observability compatibility

The supervisor emits `agent_run_started`, `agent_run_resumed`,
`agent_turn_completed`, `agent_budget_warning`, `agent_budget_exhausted`,
`agent_failure_classified`, and `agent_run_completed`. Fields include worker
class, model, reasoning effort, elapsed time, turns, retries, total tokens and
input/output tokens when Symphony exposes them. Attempt state, validation
receipt, and Git-operation state remain available in private receipts.
Compaction counts and tool-call counts are not currently exposed by the
installed Symphony state API; they remain explicitly unavailable rather than
being inferred. These events are local evidence only and do not affect
authority, routing, completion, or TTE-49's fail-open telemetry boundary.

## Migration and rollback

Migration is source-first and owner-controlled:

1. Land the reviewed source change on `v1.3-dev`; do not modify the retained
   V1.2 or legacy trees.
2. Verify the Linear labels `agent-standard` and `agent-deep`, then recapture
   and validate private metadata.
3. While the candidate gateway is stopped, use `scripts/configure.py` for any
   supported private-runtime amendment. Do not hand-edit or refresh hashes to
   hide drift.
4. Run standard and deep preflight. Keep implementation concurrency at one and
   start only the class matching the issue's sole routing label.
5. Qualify with a new, tiny, synthetic-content issue before resuming complex
   work. Preserve TTE-9 and TTE-14 as historical evidence.

Rollback stops the supervisor, restores the previously reviewed source/runtime
pair, and removes neither issues nor evidence. Existing workspaces, branches,
PRs, incident receipts, and Linear history remain intact. If only the deep
route is unhealthy, remove `agent-deep` from authorization candidates and use
standard after owner review; never auto-switch a live issue. The new private
validation and resume receipts may be retained as inert evidence.

## Validation status

Unit and integration tests cover routing fail-closed behavior, standard/deep
preflight, continuation budgets, explicit resume and replay, failure
classification, validation profile bounds and workspace binding, PR ambiguous
creation reconciliation, normal Git lifecycle, Rework reuse, and management
agents' inability to set execution labels. Symphony schema parsing and the
repository's required `make` checks are release gates.

The TTE-9/TTE-14 analysis is newly observed live evidence from the owner
runtime and Linear history. The repaired lifecycle tests use synthetic
repositories, services, issue IDs, and credentials. No claim of a successful
post-change live issue run is made until the owner completes the controlled
smoke and records its issue and PR in Linear.
