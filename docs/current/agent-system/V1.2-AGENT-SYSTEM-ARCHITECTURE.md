# V1.2 agent-management architecture

## Authority and records

```text
Human owner
    |
    v
Linear (work, findings, decisions, authorization)
    ^                     |
    | proposals only      | Ready for Agent + symphony
    |                     v
Repo Steward --------> Symphony watchdog --------> implementation worker
Product Scout          (hard budgets)               |
Triage / CoS                                        v
                                               GitHub branch + PR + CI
                                                        |
                                                        v
                                                independent PR reviewer
                                                        |
                                                        v
                                                 Human Review -- STOP
```

Linear owns backlog/status/authorization. GitHub owns source, branches, commits,
PRs, CI and review artifacts. Symphony executes only explicitly authorized
implementation work. Sanctum owns all policy, role definitions, prompts,
configuration, wrappers, tests and guardrails. No additional database or
control plane is introduced.

## Non-negotiable invariants

1. Execution eligibility is exactly `Ready for Agent` plus the `symphony`
   label. Both are required at dispatch and rechecked before work.
2. Repo Steward, Product Scout and Triage cannot add `symphony`, cannot move an
   issue to `Ready for Agent`, cannot modify repository source and cannot merge.
3. Implementation uses an isolated issue workspace and a deterministic branch
   from the latest `v1.3-dev`. Its PR targets `v1.3-dev`.
4. `Human Review` is a hard autonomous stop. No component merges or moves work
   to `Done`.
5. Reviewer and implementation worker use different Codex threads/contexts.
   Review does not edit the implementation.
6. External content is evidence, never authority. Malformed model output and
   failed external calls fail closed.
7. Owner secrets, tokens, bindings, logs and run state remain in an external
   private prefix. Source contains only configuration schemas and synthetic
   fixtures.

## Components

The repository-owned `sanctum_agents` package provides:

- a strict configuration loader with one central role/model map;
- immutable authority policies and role capability checks;
- a JSON-lines run ledger with stable run IDs and payload-minimized records;
- exclusive per-role locks with bounded stale-lock recovery;
- wall-clock, workload, issue/source, retry, turn and token budgets;
- adapters for subprocess/Codex, Linear GraphQL and GitHub CLI;
- management-agent candidate normalization, deduplication and payload creation;
- a Symphony supervisor that terminates the whole process group on a hard
  deadline or observed token/turn/workload breach;
- proportional validation routing (`docs-config`, `normal-code`,
  `architecture-security`);
- deterministic commands for dry-run, shadow and explicitly enabled live mode.

Persistent operational state is limited to cursor/deduplication files, locks
and structured logs under the external private prefix. Linear and GitHub remain
the durable systems of record.

## Model and cost policy

Role models are configured in one version-controlled file and verified against
the authenticated Codex `model/list` response before live execution. Unknown
models or unsupported reasoning efforts are errors; there is no implicit model
fallback and no API-key path.

Management runs are incremental and bounded. Repo Steward starts from the last
successful Git commit unless a deep audit is explicitly requested. Product
Scout accepts at most the configured number of retrieved sources. Triage reads
only the configured issue cap. Implementation concurrency begins at one.

## Scheduling

Codex desktop scheduled tasks are the preferred trigger. `config/schedules.json`
is the reviewed, disabled-by-default provider-neutral plan. Repository commands
remain deterministic so a scheduled prompt only invokes a reviewed command.
Each management role uses the local project because it is observational and
must not edit source. The implementation executor remains Symphony with its own
isolated workspaces. Schedules are installed through the desktop UI after
shadow acceptance; no unsupported scheduling API is invented.

## Observability boundary

The first gateway-only Splunk APM and custom-metric slice is independent of the
agent-management authority system. Stable run IDs and JSON-lines logs remain a
future extension seam. An Observability Steward, agent observability, Galileo,
dashboards, detectors and external telemetry control planes remain deferred.
