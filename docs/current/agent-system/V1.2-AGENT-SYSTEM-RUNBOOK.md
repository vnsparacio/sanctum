# V1.2 agent-system operator runbook

All commands run from the canonical Sanctum checkout. Secrets, qualified
metadata, cursors, logs, locks, artifacts, Symphony workspaces, and incident
receipts stay outside Git.

## 1. Offline readiness

```sh
.venv/bin/python -m sanctum_agents.cli validate-config
.venv/bin/python -m sanctum_agents.cli models-check
.venv/bin/python -m sanctum_agents.cli schedule-plan
make build
make test
make audit
```

`models-check` uses ChatGPT-authenticated Codex. It must fail rather than choose
a fallback model. The schedule plan must show every entry disabled while a
blocker remains.

The default private prefix is `~/.sanctum/agents-v1.2`. Override it only with an
absolute path outside the source repository:

```sh
export SANCTUM_AGENT_PREFIX=/absolute/private/agent-prefix
```

The runner creates directories as `0700` and files as `0600`.

## 2. Repeat shadow checks

```sh
.venv/bin/python -m sanctum_agents.cli run repo-steward --mode shadow
.venv/bin/python -m sanctum_agents.cli run product-scout --mode shadow
.venv/bin/python -m sanctum_agents.cli run triage --mode shadow \
  --snapshot tests/fixtures/linear-triage-snapshot.json
.venv/bin/python -m sanctum_agents.cli run reviewer --mode shadow \
  --packet tests/fixtures/reviewer-packet.json
```

Review the JSON under the private prefix's `shadow/` directory and its matching
JSONL log. A shadow pass is invalid if a repository status snapshot changes,
an external write count is nonzero, evidence is invented, or a budget stop is
misreported as success.

## 3. Linear qualification checkpoint

This is an owner-authentication checkpoint. Create or retrieve a Linear
personal token on the Mac and expose it only to the local process environment
as `LINEAR_API_KEY`; never paste it into chat, source, a prompt, or an issue.
The reproducible capture command uses the repository's narrow authenticated
client. A callable `linear_graphql` remains appropriate for ad-hoc read-only
inspection inside Symphony. Do not start the implementation dispatcher merely
to inspect metadata.

Capture the existing Sanctum V1.2 project, its owning team, workflow states,
labels and label groups, and the three expected templates with the read-only
repository command. It saves only IDs and names—not the token—to:

`$SANCTUM_AGENT_PREFIX/state/linear-metadata.json`

The file must match the synthetic shape in
`tests/fixtures/linear-metadata.json` and be mode `0600`. Validate the project
slug, Triage state, source labels, and templates before enabling writes. The
typed payload layer always targets Triage, injects a stable fingerprint,
searches the current project before creation, caps new issues, and cannot add
`symphony`.

```sh
.venv/bin/python -m sanctum_agents.cli linear-metadata-capture
.venv/bin/python -m sanctum_agents.cli linear-metadata-check
```

The capture performs no mutations and stops before replacing the snapshot on a
contract mismatch or unreviewed pagination. Any real mismatch is a stop
condition requiring a reviewed source change; do not edit the snapshot to
disguise workspace drift. The step-by-step reproduction procedure is in
[`docs/guides/linear-agent-integration.md`](../../guides/linear-agent-integration.md).

## 4. Enable one management role at a time

For each role, make a reviewed source change that sets its `write_enabled` flag
in `config/agents.json` only after metadata qualification and shadow acceptance.
Run a single `--mode live` invocation manually, inspect Linear and the private
run artifact, then enable its schedule. Repo Steward and Product Scout are
capped at one created issue per run during the initial live period. A live
Triage invocation captures its authenticated read-only snapshot automatically,
fails closed if the bounded Linear page would require pagination, and only
moves Triage items within management queues.

If the fingerprint/title search finds an existing issue, the writer records a
duplicate outcome instead of creating another issue. No management path writes
Ready for Agent or the `symphony` label.

## 5. Configure Codex desktop schedules

Codex desktop scheduled tasks are the supported trigger. Open Automations in
Codex, create each task in the saved Sanctum project, select the local project
checkout, and copy the human schedule and command from `config/schedules.json`.
Use America/Los_Angeles as the displayed timezone. Do not hand-author an
unsupported scheduler API.

Create these tasks only after the corresponding blocker list is empty:

- Repo Steward incremental: weekdays at 08:15.
- Repo Steward deep: Saturday at 09:00.
- Product Scout: Monday, Wednesday and Friday at 08:45.
- Triage: daily at 09:30, after the management runs.

The scheduled prompt should execute exactly the configured command from the
repository root, remain quiet when there is no actionable output, and report
only a failure, budget stop, candidate artifact, or required owner action. Do
not override the model in the scheduled prompt; central configuration owns it.
Locks prevent overlapping copies. Change `--mode shadow` to `--mode live` only
in the same reviewed activation that clears the blocker and enables the role.

## 6. Symphony implementation service

Set these values locally:

```sh
export SANCTUM_SYMPHONY_BIN=/absolute/path/to/reviewed/symphony
export SYMPHONY_WORKSPACE_ROOT=/absolute/private/symphony-workspaces
install -d -m 700 "$SANCTUM_PRIVATE_PREFIX/credentials/github-cli"
export SANCTUM_GIT_GH_CONFIG_DIR="$SANCTUM_PRIVATE_PREFIX/credentials/github-cli"
GH_CONFIG_DIR="$SANCTUM_GIT_GH_CONFIG_DIR" gh auth login
export LINEAR_API_KEY=... # local shell/launch context only
.venv/bin/python -m sanctum_agents.cli symphony-preflight
```

The interactive `gh auth login` is an owner checkpoint; never paste its secret
or device code into chat. Preflight verifies the canonical Git broker and
control-plane module against `SOURCE-MANIFEST.json`, requires the repository
`.venv` Python, a path-validated GitHub CLI, and the private mode-restricted
authentication directory, then reports only resolved non-secret paths. The
supervisor overrides broker executable and state variables; only the owner sets
`SANCTUM_GIT_GH_CONFIG_DIR`. Broker leases and operation receipts are created under
`$SANCTUM_AGENT_PREFIX/state/git-control-plane` with private permissions.

The reviewed Symphony binary must support `codex.turn_permission_profile`.
Sanctum selects the named `sanctum-workspace` profile in `WORKFLOW.md`; the
adapter sends `turn/start.permissions` and omits the mutually exclusive legacy
`sandboxPolicy` field.

The central `roles.implementation.wall_clock_seconds` setting is the configured
total elapsed-time budget for one Symphony implementation issue, including its
continuations. The default is 3600 seconds (one hour). To review an override,
copy `config/agents.json`, change only that positive integer, and pass the file
through the existing runner option:

```sh
.venv/bin/python -m sanctum_agents.cli \
  --config /absolute/private/agents.json symphony-preflight
```

The preflight JSON reports the resolved value as
`wall_clock_timeout_seconds`. Malformed, zero, and negative values fail config
loading. This configuration and status contract does not add or alter
kill/retry enforcement or process-termination behavior; those behaviors remain
separately reviewed runtime concerns.

Before the first real start, create a tiny documentation issue with unambiguous
acceptance criteria. The owner—not an agent—moves it to Ready for Agent and adds
`symphony`. Start only through:

```sh
.venv/bin/python -m sanctum_agents.cli symphony-run
```

Expected lifecycle: In Progress, host bootstrap from accepted
`origin/v1.2-dev`, isolated `workspaceWrite` source editing, broker commit,
broker normal push, broker-created unmerged PR to `v1.2-dev`, PR attachment and workpad
evidence, Human Review, stop. Confirm the PR is not merged, the issue is not
Done, no protected branch changed, and no credential material appears in logs
or the workpad. Then run the independent reviewer from a packet captured from
that real issue and PR.

Do not use the existing TTE-9 workspace for the first smoke. Create a trivial
documentation issue and authorize it normally with both gate conditions. Only
after that smoke reaches Human Review should the owner add one repair note to
the existing TTE-9 workpad, retire the stale workspace according to local
evidence policy, create a fresh TTE-9 workspace, and reapply the normal `Ready
for Agent` plus `symphony` gate. Never erase its failed history or mark the
failed attempt successful.

A documentation-only smoke must record its issue identifier and pull-request
URL in the Linear workpad before moving to `Human Review`.

A supervisor exit code of 75 means a budget incident, not successful work.
Read the private `incidents/<run-id>.json`, keep the issue in its active state,
and put the stop reason into its workpad before any owner-approved resume.
The same exit code is used when Symphony reports `operator_action_required`;
that blocked issue is not automatically retried during the invocation.

## 7. Release evidence

Before pushing the feature branch:

```sh
make deps
make build
make test
make audit
git diff --check
git status --short
```

Open a PR targeting `v1.2-dev`. Never merge it automatically. Preserve the
private runtime and legacy repository unchanged.
